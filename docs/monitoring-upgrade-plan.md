# Linux Traffic Monitor 新功能升级方案

日期：2026-11-02。状态：M1-A/M1-B 与 M2-A 已完成本地实现，尚未发布；M2-B/M3 待实施。实际验收进度及未验证边界见 [升级进度](monitoring-upgrade-progress.md)。本方案以升级前多 VPS 中心和 Go Agent 1.1.0 为基线，下文以升级前状态描述基线，设计目标与实际交付分别记录；已实现范围以进度文档和验证记录为准。

目标是让现有监控能够主动发现异常、解释资源瓶颈、管理流量额度，并逐步覆盖应用服务。沿用 React / Ant Design、Fastify / SQLite、Go Agent 和 HTTPS 主动上报架构，先面向单管理员、1～50 台 Linux VPS。

## 1. 当前能力与升级边界

| 领域 | 当前已有 | 本次需要补充 |
| --- | --- | --- |
| 节点 | 分组、标签、在线/陈旧/离线、停用和归档 | 事件时间线、资产到期、批量接入 |
| 资源 | CPU、内存、Swap、负载、磁盘容量快照 | 告警、容量历史、inode、CPU 等待与资源压力 |
| 流量 | 按网卡分钟历史、累计量、月周期和时区 | 套餐额度、独立计费网卡、阈值提醒、耗尽预测 |
| 磁盘 I/O | 按设备读写速率和历史、区间读写量 | IOPS、平均等待时间 |
| 网络 | 网卡流量、实时上下行速率 | ICMP/TCP/HTTP 探测、延迟、失败率与可用率 |
| 历史 | 资源及磁盘 I/O 分钟记录保留 30 天；流量长期保留 | 资源长期汇总、报表导出 |
| 可靠性 | 本地存储、分批补传、revision 去重、配置确认 | 数据覆盖说明、同步积压、持久化告警与通知重试 |

当前总览的“值得关注”仅检查节点状态、采集和配置错误；高 CPU、高内存、磁盘空间不足尚未形成资源告警。资源分钟历史没有挂载点容量指标；已有磁盘读写历史不能替代容量历史。

现有流量口径、节点凭据、登录、配置下发、历史页面、深浅主题和移动端功能继续保留。首阶段不要求重新安装 Agent。Web 终端、任意远程命令、文件管理、自动重启服务、多用户权限和 GPU 监控留作独立需求，避免阻塞本次监控升级。

相关基线：[原多 VPS 方案](multi-vps-upgrade-plan.md)、[磁盘与网卡历史设计](history-io-design.md)、[运行与迁移](operations.md)、[已有验证记录](verification.md)。

## 2. 实施阶段与交付顺序

每一阶段独立验收和发布，产品版本号在实施时确定；产品版本与数据库版本分别管理。

| 阶段 | 交付范围 | 主要改动 | 完成标志 |
| --- | --- | --- | --- |
| M1-A：告警基础 | 离线/恢复、现有资源阈值、Webhook、事件记录、维护静默 | 中心、前端；中心库迁移 | 关闭浏览器后仍能告警，中心重启后状态与待发送消息保留 |
| M1-B：流量管理 | 配额、计费口径、计费网卡、80/90/100% 提醒、基础预测 | 中心、前端 | 与原始分钟记录核对一致；跨周期和补传不重复提醒 |
| M2-A：网络质量 | 能力协商、ICMP/TCP/HTTP、证书到期、探测历史 | 协议、Agent、中心、前端 | 新旧 Agent 可混用，探测与补传不阻塞原采集 |
| M2-B：系统诊断 | 容量/inode 历史、iowait/steal、PSI、IOPS、TCP 指标、服务状态 | 协议、Agent、中心、前端 | 权限不足有明确状态，能从告警跳转到对应指标历史 |
| M3：运行管理 | Docker/重点进程、资产到期、批量接入、长期汇总、定时报表 | 按功能拆分实施 | 每个模块可独立启用，已有统计和权限边界通过回归 |

依赖关系：M1-B 复用 M1-A 的事件与通知；M2-A 先交付能力协商和扩展配置，再增加探测；M2-B 复用扩展协议；M3 各模块以已验收阶段为基础。第一批实施范围固定为 M1-A、M1-B，暂不把后续全部指标塞进同一次变更。

## 3. M1-A：告警中心与通知

### 3.1 规则与默认模板

规则包括名称、节点范围、指标及对象、触发阈值、持续时间、恢复阈值与持续时间、严重级别、通知渠道、重复提醒间隔、启用状态。节点范围支持单节点、指定节点集、分组/标签及全部启用节点；保存时显示匹配预览，后续成员变化记录事件。

提供下列模板，默认未启用，由管理员选择节点和渠道后保存；阈值均可调整。

| 规则 | 默认触发条件 | 默认恢复条件 |
| --- | --- | --- |
| 节点离线 | 距最后上报超过 120 秒 | 连续 30 秒有新鲜上报 |
| 数据陈旧 | 采样停滞持续 120 秒 | 新鲜样本连续出现 30 秒 |
| CPU 高占用 | 超过 90%，持续 5 分钟 | 低于 80%，持续 2 分钟 |
| 内存高占用 | 超过 90%，持续 5 分钟 | 低于 85%，持续 2 分钟 |
| 磁盘容量 | 指定挂载点使用率超过 90%，持续 5 分钟 | 低于 85%，持续 2 分钟 |
| 流量额度 | 本周期达到 80%、90%、100% | 新周期重新计算，不按瞬时下降发送恢复 |

支持绝对剩余空间规则，例如剩余不足 5 GiB；高带宽规则须先填写节点带宽容量，统一明确 Mbps 与 B/s 的换算。M1 不做自动学习型流量异常检测。

节点列表原有 15 秒陈旧、45 秒离线状态阈值不变，展示状态与通知等待时间分开解释。待接入、停用、归档节点不触发离线告警；恢复启用后给予首次上报宽限期。宽限期结束仍无上报时产生“启用后未上报”事件。

### 3.2 判定与事件生命周期

- 中心每 5 秒执行独立判定任务，离线判定不依赖收到新上报，也不依赖浏览器连接。单中心进程运行，防止同一任务重入。
- 条件状态为 `normal → pending → firing → recovering → normal`；事件记录首次异常、确认触发、最近异常、恢复和关闭原因。规则变更或停用导致的关闭标为“配置关闭”，不伪装成指标恢复。
- 数据有效性单独记录为 `fresh / unknown / unsupported`。资源规则只用新鲜样本；缺失、陈旧、不可读、时钟异常不能作为零值或恢复证据。
- 已触发事件遇到数据中断时保持未恢复，并标注数据未知；尚在持续时间累计中的规则中断后重新计时。重复 revision 不推进持续时间。
- 同时核对中心接收时间、样本 `observed_at` 与最后有效样本间隔。超过 15 秒没有有效新样本，或样本时间明显超前时，资源判定进入未知；不因为历史补传刷新了接收时间就认定资源健康。原有上报时钟校验继续保留。
- 告警状态、事件和待发送消息在同一数据库事务中写入。中心重启后恢复状态，但不把服务停止期间当成连续有效采样。
- 维护窗口按节点或分组配置起止时间，内部使用 UTC、页面按选定时区展示；窗口内继续采样和记录事件，暂停通知。结束时仅汇总仍然存在的异常，已在窗口内恢复的事件不补发。
- “已读/确认”只改变人工处理标记，不改变指标状态。支持有限期静默。停用、归档或规则删除时取消相关待发送消息，并记录关闭原因。

### 3.3 通知投递

首版实现通用 HTTPS Webhook，采用固定 JSON 模板，包含稳定事件 ID、节点名称、规则名称、严重级别、触发/恢复时间、当前值、阈值和详情链接。后续再加 Bark、Telegram、邮件适配器。

- 数据库 outbox 保存消息，独立 worker 发送，默认并发 2、单次超时 10 秒，不在 Agent 上报事务中请求通知服务。
- 网络异常、408、429、5xx 最多自动尝试 5 次，间隔 30 秒、2 分钟、10 分钟、30 分钟；429 可采用有上限的 `Retry-After`。其他 4xx 标记失败并提示检查配置。发送成功以 2xx 为准。
- 同一事件、事件阶段、渠道和提醒序号建立唯一约束；远端已接收但本地未记账时可能重试，因此定义为至少一次投递，Webhook 携带稳定幂等键，不能承诺跨系统绝不重复。
- 同一事件的触发和恢复按顺序投递。首次触发仍未投递就已恢复时，合并成“异常已恢复”摘要；已经成功投递触发消息则正常发送恢复。
- 默认只发送首次触发和恢复；周期提醒显式开启。发送前重查静默、规则和节点状态，失效消息取消。跨多个阈值时合并为当前最高级别。
- 页面显示成功/失败、脱敏错误、尝试次数和下一次重试时间，支持限流的测试通知与手动重试。
- Webhook URL、鉴权头等按秘密处理：API 脱敏返回，日志和审计不记录原文。含秘密的配置使用中心挂载的密钥文件加密存储，密钥与数据库分别备份；未配置密钥时禁用渠道保存，不影响原监控启动。
- 外发目标仅允许 HTTP(S) 中约定的安全配置，生产默认 HTTPS、验证证书、不自动重定向；拒绝 URL 用户信息和云元数据地址。私网目标需显式配置允许的主机/网段，解析与实际连接共同校验，避免通知配置变成任意内网请求入口。

## 4. M1-B：流量额度与预测

### 4.1 独立套餐配置

中心新增 `traffic_policies`，与已有 Agent `MonitorConfig` 分开存储。字段包括额度字节数、输入单位、计费方向、计费网卡、提醒阈值、启用状态和策略版本。

- 额度未设置表示不启用；启用时额度必须大于零。输入支持 GB/TB 与 GiB/TiB，保存为整数字节，展示单位保持一致。
- 首版沿用节点现有月起始日、起始时间、IANA 时区，不另建第二套周期。界面显示周期的完整起止时间。
- 计费网卡必须显式选择；新建策略可预选当前监控网卡，但保存后固定列表。改变 Agent 采集网卡时提示检查计费网卡，不静默改写套餐。
- 原节点总流量和全局总流量定义不变；套餐区域单独显示“计费流量”。计费网卡未被采集或历史不完整时提示缺口。

先汇总所选网卡在周期 `[start, end)` 内的 RX、TX，再按下列公式计算；`max` 不能按每分钟分别取大值后相加。

| 类型 | 计费流量 |
| --- | --- |
| `tx` | 周期上传总量 |
| `rx` | 周期下载总量 |
| `sum` | 周期上传 + 下载总量 |
| `max` | 周期上传总量与下载总量中的较大值 |

中心用 BigInt 做汇总和阈值比较，JSON 用十进制字符串；允许多个合法 64 位计数汇总后超过单个 64 位整数，避免先在 SQL `SUM` 中溢出。百分比最后再转换为展示数值。

### 4.2 提醒、重算和预测

- 阈值提醒唯一键包含节点、周期开始时间、策略版本、阈值。重复上报、中心重启、同周期补传不重复触发同一阈值。
- 修改额度、方向、计费网卡或周期后，显示重算预览并记录策略版本；保存后最多生成一次当前最高阈值通知，注明“配置变更后重算”。
- 补传更新当前周期时允许产生新的阈值提醒，但合并已跨过的低档位；补传到已结束周期只更新历史报表，不发送过期额度提醒。
- 预测展示剩余额度、周期剩余时间、预计周期末用量、预计耗尽时间；已超额显示已超额，近期有效速率为零时显示无法估算耗尽时间。
- 初版取最近最多 7 个已结束的节点本地自然日，至少 3 天有效数据，要求所选计费网卡的分钟记录覆盖率均达到 95%。按真实时长加权计算 RX/TX 平均速度，分别投影后应用计费公式；夏令时日不固定当作 24 小时。
- 计费 `max` 的耗尽时间取 RX、TX 各自到达额度的最早时刻，不能用逐分钟最大速率替代。预测标明窗口、覆盖率和估算属性。
- 现有协议不能证明全部历史已补齐，也不能证明补记分钟代表连续采样。M1 明确展示“基于中心已收到记录估算”；覆盖不足或当前采样异常时隐藏预测，不补零。M2 再结合积压和同步水位提高可信度。

首版预测仅展示，不直接触发自动限速、停机或预测型告警。服务商账单口径与接口计数可能不同，不宣称预测或统计等同于账单。

## 5. M2-A：网络质量与 HTTP 服务探测

### 5.1 探测任务

任务包含执行节点、目标、协议、IPv4/IPv6、间隔、超时、启用状态和任务配置版本。同一目标可绑定多个执行节点，图表明确“来源节点 → 目标”，不同方向分别统计。

| 协议 | 首版参数 | 结果 |
| --- | --- | --- |
| ICMP | 主机、IP 版本、每轮 1 次请求 | RTT、应答/超时、实际请求丢包率 |
| TCP | 主机、端口、IP 版本 | TCP 建连耗时、成功/失败、失败原因 |
| HTTP(S) | URL、GET/HEAD、预期状态码范围 | 状态码、总耗时、DNS/TCP/TLS 阶段耗时（可用时） |
| HTTPS 证书 | HTTPS 目标 | 到期时间、剩余天数、证书校验错误 |

默认每 60 秒一次、超时 3 秒；最小间隔 15 秒，每节点默认最多 10 个任务、并发 2。采用独立调度与有界队列，目标超时不得阻塞原有 1 秒网络采样和 5 秒资源采集。错过执行时刻不补跑过去的请求，记录为漏采；各节点启动偏移分散请求，但不因失败自动改变配置的监控周期。

DNS、TCP、TLS、HTTP 状态失败分别记录。TCP/HTTP 展示“探测失败率”，不称作 IP 丢包率；权限不足、任务被跳过、Agent 离线均为无有效观测，不算目标故障。ICMP 使用非 root 可用的 ping socket 或最小所需能力；无法使用时提示不可用，不自动将整个 Agent 切换为 root。

HTTP 首版不支持任意脚本、请求体和任意鉴权头；限制响应体读取大小，不存储响应正文，不跟随重定向。URL 查询参数可能含秘密，配置与错误信息须脱敏。私网服务通过 Agent 本地允许的目标范围显式启用，默认阻止云元数据、链路本地等敏感目标；DNS 校验覆盖实际连接地址。

### 5.2 结果、历史与告警

- 探测结果记录 `sample_id`、同步 revision、任务版本、计划/开始/完成时间、状态、实际执行次数、耗时、脱敏原因；`source_id + sample_id` 唯一，迟到或重复结果不重复累计。
- Agent 断网仍按已保存配置探测并保存结果；网络恢复后独立分页补传。移除或禁用任务后停止调度；旧版本结果可以入历史，但不能覆盖当前状态或触发新版本告警。
- 展示最近结果、延迟曲线、P50/P95、ICMP 丢包率或 TCP/HTTP 失败率、观测可用率、覆盖率。无记录区域为空缺。
- 观测可用率为成功次数 / 有效执行次数，覆盖率为有效执行次数 / 应执行次数；显示统计窗口和分母，不把漏采视为 100% 可用。
- P95 由窗口内真实成功样本计算，不平均各分钟 P95。M2 查询范围限于保留的原始记录；M3 长期统计另存可合并直方图或分位数摘要。
- 默认连续 3 次有效失败后告警、连续 2 次成功后恢复；跨缺口不累计连续次数。证书到期模板为 14/7/3 天，每档去重。

## 6. M2-B：系统诊断与监控自身

| 能力 | 数据与口径 | 默认采集建议 |
| --- | --- | --- |
| 文件系统 | 挂载点、容量/可用空间、inode 总量/已用/剩余 | 30 秒采集，按分钟存历史；容量与块设备 I/O 分开展示 |
| CPU | user/system/iowait/steal、核数归一化负载 | 5 秒；基于计数器差值，首次或重置时为空 |
| 内存 | 可用量、Swap 换入/换出、内存 PSI | 5 秒；无 Swap 与不可读分开 |
| PSI | CPU/内存/I/O 的内核可用压力字段 | 5 秒；缺少内核支持标为 unsupported |
| 磁盘 I/O | 读写 IOPS、读写平均等待时间 | 5 秒；与现有设备过滤和基线重建规则一致 |
| 网络协议 | TCP 状态数、重传计数/速率、网卡包数/错误/丢弃 | 15 秒；计数器重置不产生负数或尖峰 |
| 服务 | 指定 systemd unit 或 OpenRC 服务的运行状态 | 30 秒；只查询明确配置的服务，不执行自定义命令 |
| Agent 自身 | 版本、启用能力、采集错误、同步积压数量/最早时间、上次成功确认 | 30 秒；快照与各历史流分别显示同步状况 |
| 中心自身 | 数据库大小、上报耗时、判定任务延迟、通知队列和失败数 | 30 秒；后台诊断页面，不公开凭据或完整日志 |

新增低频指标分别携带采样时间，新鲜度默认取 `max(15 秒, 3 × 采集周期)`；不能直接套用 M1 的 5 秒资源采样窗口，也不能用节点心跳代替该指标更新。连续阈值只由对应指标的新样本推进，节点离线仍按现有连接状态处理。

IOPS 使用操作次数差值 / 有效观测秒数；平均等待时间使用对应读写耗时差值 / 操作次数差值。无操作时等待时间为空、IOPS 为零；设备重置或采样间断按现有规则重建基线。容量历史增加文件系统身份信息，挂载点被不同文件系统复用时中断趋势，不能连续外推。

磁盘写满预测至少需要 3 天有效容量历史，扩容、换盘或大规模清理后重新建立趋势。steal、PSI 等作为排障证据展示，不直接断言某个服务商或应用故障。

旧 Agent 或权限不足时展示“待升级 / 未启用 / 不支持 / 不可读”，不填充零。非 root Agent 默认权限继续保留；systemd 与 OpenRC 分别验收。

## 7. M3：按需要增加的管理能力

1. **Docker 监控**：容器身份、运行/健康状态、重启次数、CPU、内存、网络、I/O。使用稳定容器 ID 与名称分开建模，明确 CPU 百分比是否可超过单核 100%。仅监控，不增加启动/停止/exec 操作；Docker socket 本身权限很高，优先使用受限 API 代理，不能把挂载 `:ro` 当成只读 API 权限。
2. **重点进程**：白名单进程存活、CPU/内存，Top N 默认 10、每 30 秒采集。不保存完整命令行、环境变量或任意文件内容；进程退出后保留历史，身份包含启动时间以应对 PID 复用。
3. **资产与到期**：供应商、地区、IP、备注、价格、币种、账期、到期日、带宽；价格用最小货币单位整数存储，不同币种分开汇总。到期前 30/7/1 天去重提醒，修改日期重算；不代替用户续费。
4. **批量接入**：短期、限次数、可撤销的注册凭据换取每节点独立凭据；自动识别 amd64/arm64 与 systemd/OpenRC，校验下载文件，已有安装先检查再处理。注册凭据不暴露到 URL、访问日志或历史命令中，安装失败可重试，不覆盖现有数据目录。
5. **长期历史**：资源与磁盘小时汇总保存 1 年、天汇总保存 3 年；原始 30 天记录清理前确认汇总已提交。迟到记录按受影响桶重算，平均值用有效样本数/观测时长加权，最大值与覆盖率单独保存。流量原始分钟记录继续长期保留，不能用 UTC 日汇总替代任意时区和分钟边界的计费周期。
6. **报表与导出**：节点/分组日周月报、可用率、故障时长、流量与容量趋势；用户选择日历月或节点计费周期。定时任务按时区执行、任务周期唯一去重，停机恢复只补最近一期并标明迟发。CSV 有分页/大小上限并处理公式注入，导出沿用管理员权限。

## 10. API 与协议兼容

### 10.1 新增管理接口草案

所有路径以 `/api/v1` 为前缀，沿用管理员 Cookie、Origin 和 CSRF 校验；列表统一分页、限定时间范围与数量。

| 方法与路径 | 用途 |
| --- | --- |
| `GET/POST /alert-rules`，`PATCH/DELETE /alert-rules/:id` | 规则列表、创建、修改、停用删除 |
| `GET /alerts`，`GET /alerts/:id`，`POST /alerts/:id/acknowledge` | 告警查询、详情、人工确认 |
| `GET/POST /maintenance-windows`，`PATCH/DELETE /maintenance-windows/:id` | 维护与限期静默 |
| `GET/POST /notification-channels`，`PATCH/DELETE /notification-channels/:id` | 渠道管理；读取只返回脱敏字段 |
| `POST /notification-channels/:id/test`，`GET /notification-deliveries`，`POST /notification-deliveries/:id/retry` | 试发、投递记录、人工重试 |
| `GET/PUT /nodes/:id/traffic-policy`，`POST /nodes/:id/traffic-policy/preview` | 套餐读取、保存与重算预览 |
| `GET /nodes/:id/quota`，`GET /nodes/:id/events` | 额度/预测和事件时间线 |
| `GET/POST /probe-tasks`，`PATCH/DELETE /probe-tasks/:id` | 探测任务与节点分配 |
| `GET /nodes/:id/probe-history`，`GET /nodes/:id/system-history` | 新指标历史；返回覆盖率、能力与缺失原因 |

删除规则或任务采用逻辑停用/归档，保留其事件和历史关联。套餐配置只属于中心，不放进现有 Agent `ConfigSchema`，避免旧 Agent 忽略新字段却确认整个配置已应用。

### 10.2 扩展上报协议

当前协议为 v1，多个 schema 设置了 `additionalProperties: false`；旧中心会拒绝陌生字段。不能仅在新 Agent 上添加字段就宣称双向兼容。

1. M1 保持上报请求和原有配置不变，新中心继续接受旧 Agent。
2. M2 新中心在上报响应增加可选 `server_capabilities`；新 Agent 初次连接只发送旧中心可接受的基础字段，不携带尚未协商的扩展。
3. 确认中心支持后，新 Agent 才发送可选 `capabilities` 以及受支持的扩展快照和历史数据流。能力包含具体版本，不靠 Agent 版本字符串猜测。
4. 新中心给支持扩展的 Agent 下发独立 `extensions_config` 与 `extensions_config_version`；Agent 校验、原子持久化后返回独立应用版本和错误。基础配置与扩展配置分别确认，旧 Agent 的页面显示“不支持”，不显示“已应用”。
5. 新增历史流拥有独立分页和 ACK，沿用单调 revision、事务提交后确认、确认与发送批次精确匹配的约束。缺少 ACK 不推进该流，不能把一个扩展流的最大 revision 当成所有流的确认值。
6. 连接建立或重连时先用基础字段重新协商。扩展上报被 schema/版本校验拒绝时，仅再做一次基础协议能力探测，不推进被拒批次的游标，也不吞掉其他鉴权或校验错误；只有收到合法响应才能更新能力。中心能力消失或降级时，停止发送扩展字段，暂停未被支持的远程探测任务，保留新历史等待恢复或按明确期限清理。发送基础资源时投影掉扩展字段，包括已持久化分钟记录中的新键。
7. 总请求体继续小于当前 Fastify/Nginx 的 2 MiB 限制；各流最多 256 条且另有总体字节预算，轮询分配预算以防流量或探测积压独占。磁盘/基础资源/流量各流既有 ACK 语义不变。

新增字段同时更新 TypeScript schema、导出的 `report.schema.json`、Go 类型、样例及契约测试。缺失能力、字段为空、未启用和读取失败分别编码，不能通过补零通过校验。

## 11. 升级、备份与回退

当前中心与 Agent 数据库均为 `user_version=2`。后续由各自的迁移序列逐次升级，M1 只升级中心库，M2 才涉及 Agent 库；不预设两个库版本永远相同。

1. 在测试环境用当前版本数据库副本验证迁移，包括已存在节点、历史、凭据摘要、会话、配置和同步游标；新模块初始关闭，不自动产生真实外发通知。
2. 生产变更前保留原镜像标签/摘要、Agent 二进制、部署配置，分别对中心和 Agent 做 SQLite 一致性备份；新增通知密钥单独安全备份。不能只复制运行中 SQLite 的主文件而遗漏 WAL。
3. 先升级中心并确认旧 Agent 仍可上报，再启用 M1 功能。M2 先选择一台 Agent 试运行，核对旧流量、配置确认、补传、新指标后逐批升级。
4. 迁移在事务中执行，失败停止启动并输出脱敏错误；不能清空数据库重新初始化。正常升级不更换节点凭据或 source_id。
5. 现有旧程序会拒绝高版本数据库，回退必须停止新服务并恢复匹配的程序、数据库和配置备份；仅替换二进制不能视为可用回退。
6. 若中心库恢复到较早时刻，Agent 的已确认游标可能领先于恢复后的中心。正式发布前提供并验收“重新同步指定时间范围/重置同步游标”的显式运维工具：停止对应 Agent 后操作其游标，保留 source_id 和本地记录，通过 revision 幂等补传。M1 以兼容现有 v2 Agent 库的独立维护工具提供，不要求替换常驻 Agent。
7. 超过 Agent 保留期限的资源或探测记录、只保存在中心的新配置/通知记录，恢复旧备份后可能无法重建，回退前需明确备份时点和可恢复范围。原有分钟流量本地长期保存，可用于重传核对。

如果还需要恢复 Agent 数据库备份，须单独检查累计量、原始计数器基线、revision 序列和中心已接收水位。恢复前保存可读数据库及序列高水位；维护工具必须防止序列回退导致新数据被中心忽略，并为需重传的记录分配有效的新 revision。无法核实流量基线时暂停恢复步骤并说明缺口，不能直接让旧库上线后覆盖较新的累计值。

部署实施时分别检查迁移、容器/服务状态、实际访问页面、Agent 上报和通知结果。本地构建、模拟通知和交叉编译分别记录，不能替代公网通知、真实 VPS 与 arm64 设备验证。本方案本身不执行部署、数据迁移或凭据更换。

## 12. 验收标准

### 12.1 M1 必须通过

- 旧 Agent、原历史 API、配置下发、SSE、流量累计和自定义周期回归通过；新增套餐不能改变原总流量。
- 离线、恢复、持续阈值、滞回、数据缺失、重复样本、补传、规则变更、静默和停用/归档均有可控时钟测试。
- 重启后活跃事件不丢失，未投递消息继续处理；模拟发送成功但落库前退出，验证稳定幂等键和至少一次语义。
- 覆盖 Webhook 超时、429、5xx、4xx、重定向、私网允许规则、日志脱敏、密钥缺失、加密配置备份恢复。
- 配额覆盖月末、31 日、闰年、夏令时、时区/网卡修改、四种计费公式、大整数、跨档合并和过去周期补传。
- 预测覆盖不足、零流量、已超额、`max` 方向切换及夏令时，不显示假精确结果。
- 浏览器完成规则创建→测试通知→触发→确认→恢复，套餐编辑→预览→保存→周期核对，并检查深浅主题、手机和键盘流程。

### 12.2 M2/M3 增量验收

- 新中心配旧 Agent、新中心配新 Agent、新 Agent 配缺少扩展能力的中心均通过契约测试；未知字段、配置保存失败、缺失 ACK 和超预算分批均有测试。
- 探测使用隔离本地 HTTP/TCP/DNS 测试服务验证成功、超时、失败分类、证书临期、IPv4/IPv6、不追补过期任务、配置版本切换与多源结果去重；ICMP 另测有权限和无权限场景。
- 补传按流独立推进；确认丢失、进程重启、旧任务结果、历史过期和重新同步均可恢复或明确标注缺口。
- 采集测试覆盖首次、重启、计数器归零、换盘、挂载点复用、无 Swap、PSI 不支持、权限不足和零操作。
- 长期汇总验证加权平均、最大值、空缺、分位数摘要合并、迟到记录重算、清理先后顺序；计费仍可按分钟边界重算。
- Docker、systemd、OpenRC、真实 HTTPS 通知及 arm64 运行分别记录实际环境；未完成的项目明确标注未验证。

### 12.3 性能与检查命令

容量测试沿用 50 节点目标，新增每节点最多 10 个探测任务及代表性的 30 天资源历史；同时执行上报、查询、SSE、告警和通知重试。用相同硬件/数据集对比升级前后，建议门槛为上报 P95 增幅不超过 20%、总览 P95 小于 1 秒、历史查询 P95 小于 2 秒、常态告警调度延迟小于 10 秒。超标先分析索引、批量写入和任务调度，再决定调优；这些是待验证目标，不是已有性能结论。

先运行对应功能的最小测试，再执行发布检查：

```bash
npm test
npm run typecheck
npm run build
npm run test:e2e
```

涉及 Agent 的阶段，在 `agent` 目录执行：

```bash
GOCACHE=/tmp/traffic-monitor-go-cache go test -race ./... -count=1
GOCACHE=/tmp/traffic-monitor-go-cache go vet ./...
```

另执行 amd64/arm64 交叉编译、协议 schema 一致性、数据库迁移/恢复演练，以及部署相关的 Compose 配置和隔离 Docker 启动检查。每阶段将实际命令、结果、截图和未验证边界写入 `docs/verification.md`；不要把本节验收计划写成已通过记录。
